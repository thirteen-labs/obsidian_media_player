# obsidian-media-player

Plug-and-play media toolkit for **React + React Native** — one package for **Video**, **Audio** and a full-featured **Music** player. Think `react-native-video` + `expo-av` + `react-native-track-player`, unified under a single idiomatic API. Works on **iOS, Android, and Web** (via `react-native-web`).

- Bare RN, **no Expo dependency** (but ships an **Expo config plugin**). Autolinked via `react-native.config.js` + `ObsidianMediaPlayer.podspec` / `build.gradle`.
- **New Architecture only on iOS** — requires `RCT_NEW_ARCH_ENABLED=1`; `pod install` fails with instructions if it is unset. The Old Architecture (Paper) was dropped in 0.5.0: the TurboModule specs only register under Fabric, and the video surface renders through Fabric's legacy-view-manager interop layer. Android works on both architectures. Built with `react-native-builder-bob` (`lib/commonjs`, `lib/module`, `lib/typescript`).
- Video backed by **AVPlayer + AVPlayerLayer** (iOS) and **ExoPlayer + TextureView** (Android, `androidx.media3`) with an **HTML5 `<video>` fallback on web** (`src/components/Video.web.tsx`).
- Audio / Music backed by **AVPlayer** (iOS, `AVAudioSession` + lock-screen) and **ExoPlayer + MediaSession** (Android, `androidx.media3:media3-session`) with an **HTMLAudioElement fallback on web** (`src/components/Audio.web.tsx`).
- HLS / DASH adaptive streaming (type-aware `MediaSource.type` + `HlsMediaSource`/`DashMediaSource`), per-source **headers + `cacheable`** forwarding, a shared **200 MB disk cache**, **offline downloads** (`DownloadManager` / `ObsidianCache`), **background audio** (service-owned player + `MediaSession` on Android, audio session on iOS), **lock-screen / headset / car remote controls on all native platforms**, playlist with **shuffle / repeat**, and a typed **Casting** surface (`CastManager` + `CastProvider`) ready to wire to Chromecast / AirPlay.
- **DRM is not supported.** See [Not supported](#not-supported) — `drmLicenseUri` was removed in 0.5.0 rather than left as a non-functional passthrough.

## Install

```bash
npm i obsidian-media-player
# iOS
pod install --project-directory=ios
# Android: no extra step (autolink)
# Web: no extra step — Video/Audio fall back to <video>/<audio> via react-native-web
```

`react-native >= 0.74`, `react >= 18`, iOS 13+, Android `minSdk 24`, Web `react-native-web >= 0.19`.

> The RN floor was `0.73` until `0.5.0`. It was never true: the module extends
> `BaseReactPackage`, which does not exist before RN 0.74, so an app on 0.73
> failed to compile rather than to run. Verified with `npm run verify:android`
> across RN 0.73.6 / 0.74.0 / 0.80.0 — see `to-be-done.md` FG-0.7.

Build outputs are generated by `react-native-builder-bob` (`npm run prepare` → `lib/commonjs`, `lib/module`, `lib/typescript`); `react-native` field in `package.json` points to `src/index.ts` for Codegen.

### Expo (optional)

```json
// app.json
{ "plugins": [["obsidian-media-player/plugin", { "backgroundAudio": true }]] }
```

The plugin (`plugin/index.js`) adds `UIBackgroundModes: audio` to `Info.plist` and keeps the Android `FOREGROUND_SERVICE`/`mediaPlayback` manifest in sync. Without Expo, add it manually (see Permissions below).

### Permissions

**iOS** `Info.plist`:

```xml
<key>UIBackgroundModes</key><array><string>audio</string></array>
```

**Android** — the library manifest already declares everything playback needs
(`INTERNET`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `WAKE_LOCK`
and the `ObsidianPlaybackService` with `foregroundServiceType="mediaPlayback"`),
so the manifest merger propagates these into your app automatically. Your app
only needs to request the **runtime** permission for the notification itself on
Android 13+:

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
```

> `FOREGROUND_SERVICE_MEDIA_PLAYBACK` is not optional. Since API 34, a
> `mediaPlayback` foreground service that lacks it throws `SecurityException`
> from `startForeground()`. The library declares it; if you ship a hand-written
> manifest, keep it.
>
> On Android 13+, the service runs regardless of `POST_NOTIFICATIONS`, but the
> notification itself is invisible without it — which looks identical to
> "background playback is broken". Request it before calling
> `setBackgroundEnabled(true)`.

When you enable background playback the module configures `AVAudioSession.category = .playback` (iOS) and starts `ObsidianPlaybackService` as a foreground service with a `MediaSession` (Android). Make sure your app enables the audio background mode / foreground-service type `mediaPlayback` if you ship a custom manifest.

## Quick start

```tsx
import { Video, Audio, MusicPlayer, MediaProvider, usePlaybackState } from 'obsidian-media-player';

// Video — renders a native surface
<Video
  source={{ uri: 'https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8', type: 'hls' }}
  paused={false}
  resizeMode="contain"
  onStateChange={s => console.log(s.status, s.position)}
/>

// Audio — headless
import { useAudioPlayer } from 'obsidian-media-player';
const { state, controls } = useAudioPlayer();
controls.load({ uri: 'https://.../song.mp3' });
controls.play();

// Music player — headless, with a full queue
<MusicPlayer
  tracks={[
    { id: '1', source: { uri: 'https://.../1.mp3' }, title: 'One', artist: 'Obsidian' },
    { id: '2', source: { uri: 'https://.../2.mp3' }, title: 'Two', artist: 'Obsidian' },
  ]}
  repeatMode="queue"
  shuffle={false}
  remoteControls={{ enablePlayPause: true, enableSkip: true, enableSeek: true }}
/>
```

### Imperative handles

```tsx
const ref = useRef<VideoHandle>(null);
<Video ref={ref} source={...} />
ref.current?.seek(30);
ref.current?.pause();

// Audio / Music expose the same shape via their hooks
const { controls } = useMusicPlayer(tracks);
controls.next(); controls.setShuffle(true);
```

### App-wide player with context

```tsx
import { MediaProvider, useMedia } from 'obsidian-media-player';

<MediaProvider initialTracks={tracks} remoteControls={{ enablePlayPause: true }}>
  <App />
</MediaProvider>

// anywhere inside:
const { state, controls, next, toggle } = useMedia();
```

`controls` is a stable object whose methods resolve to the mounted player at
call time, so it is safe to capture in a callback or a dependency array.

### Derived playback state

```tsx
const d = usePlaybackState(state);
// d.isPlaying, d.isBuffering, d.isEnded, d.progress (0..1)
```

### Remote commands (lock screen / headset)
```tsx
import { useRemoteControls } from 'obsidian-media-player';
useRemoteControls((cmd, payload) => {
  if (cmd === 'next') controls.next();
  if (cmd === 'seek') console.log(payload);
});
```

Works on **iOS** (`MPRemoteCommandCenter`), on **web** (`navigator.mediaSession` —
OS media keys, lock screen, car stereo), and on Android only once FG-4.1 lands. On
web the browser's seek actions send a *delta* while the native platforms send an
absolute position, so the hook adds the current position itself. Pass `getState` so
it can:

```tsx
useRemoteControls(onCommand, () => player.getState());
```

Without it, `seekbackward` / `seekforward` resolve to `position: 0`. `stop` is
part of the `RemoteCommand` union. Every web entry point is feature-detected, so
Firefox without `mediaSession`, an old Safari, and server-side rendering all
degrade to a no-op rather than throwing.

### Playlist helpers

```ts
import { buildOrder, createQueue, nextCursor } from 'obsidian-media-player';
```

### Casting (provider stub)

```ts
import { castManager } from 'obsidian-media-player';
castManager.isSupported; // false until a provider is registered
await castManager.discover(); // -> [] until a real provider is wired
```

No Cast SDK is bundled, so app-driven discovery/pick is not implemented yet —
`connect()` without a provider rejects with an actionable error instead of
pretending. Wire a real backend (Google Cast SDK, `AVRoutePickerView`, or your
own) via `castManager.registerProvider(provider)` without changing the public
API. *System* AirPlay already works on iOS (the audio session opts in via
`.allowAirPlay`); only app-initiated casting is missing.

### Offline downloads & cache

```ts
import { DownloadManager } from 'obsidian-media-player';

if (!DownloadManager.isSupported) return; // hide the button rather than offer a no-op

const info = await DownloadManager.download('track-1', {
  uri: 'https://cdn.test/track.mp3',
  headers: { Authorization: `Bearer ${t}` }, // works on web too
});
info.bytesTotal;

const downloads = await DownloadManager.getDownloads(); // DownloadInfo[]
await DownloadManager.removeDownload('track-1');
await DownloadManager.clearCache();
const bytes = await DownloadManager.getCacheSize();
```

**`download()` rejects on failure.** It used to swallow every error, so a 404, an
expired token and a CORS block were all indistinguishable from success. Each now
rejects with a message saying which it was. `download()` also returns the stored
`DownloadInfo` (it used to return `void`), so you can read the byte count without a
second `getDownloads()`.

**`isSupported`** is a getter, not a constant — `caches` is absent outside a secure
context, so it reflects the environment when you read it. Use it to hide a download
UI rather than letting someone click into a no-op.

**On web, `hls` / `dash` downloads are refused**, headers or not. Playing a
segmented stream works because the element fetches the manifest and its segments
itself; *storing* it does not, because a cache entry holds one body. Downloading
the manifest alone would save something unplayable.

Native: Android `ExoPlayerProvider` `SimpleCache` (200 MB LRU) + `Hls/DashMediaSource.Factory` with `CacheDataSource`; iOS `ObsidianCacheModule` (`AVAssetDownloadTask` hook for HLS when FairPlay entitlement is present). Web uses `CacheStorage`, keyed by download id so removal and listing work. Also exposed as `CacheNative` (`ObsidianCache` TurboModule) and via `headers`/`cacheable` on `MediaSource`.

### Web

Every component and hook has a `.web` implementation, auto-picked by Metro for `Platform.OS === 'web'`. The same JSX works on `react-native-web` / Next.js without touching native code:

| | Web implementation |
|---|---|
| `<Video>` | `components/Video.web.tsx` — HTML5 `<video>` |
| `<Audio>` | `components/Audio.web.tsx` — HTML5 `<audio>` |
| `<MusicPlayer>` | `components/MusicPlayer.web.tsx` — one `HTMLAudioElement`, queue logic shared with native via `core/PlaylistManager` |
| `useMusicPlayer` | real shuffle / repeat / skip / seek / next / previous over that element |
| `useAudioPlayer` | real transport + progress |
| `useVideoPlayer`, `usePlaybackState`, `MediaProvider`, `useMedia` | shared, no platform branch |

The web build is a genuine media player, not a compatibility shim. What it cannot do is listed under [Not supported](#not-supported) — those are browser limits, not omissions.

Importing the package on web is a gated build: `npm run bundle:web` bundles the entire public surface for the browser and fails if anything in the graph reaches for a native-only module. It is run in CI, and it exists because a web bundle is the only thing that catches this class of break.

### Expo plugin

See Install → Expo. Source: `plugin/index.js` (`withObsidian`). Disable with `{ backgroundAudio: false }`.

### Headers / cacheable

`MediaSource` fields wired end-to-end:

```ts
<Video source={{
  uri: 'https://cdn.test/secure.m3u8',
  type: 'hls',
  headers: { Authorization: 'Bearer ...' },
  cacheable: false // bypass disk cache
}} />
```

Android builds a per-source `Hls/Dash/ProgressiveMediaSource` with `DefaultHttpDataSource` headers and `CacheDataSource` toggle; iOS passes `AVURLAssetHTTPHeaderFieldsKey`.

> **DRM was removed in 0.5.0.** `MediaSource.drmLicenseUri` used to be accepted and
> then discarded by both platforms, so protected content failed as a bare network
> error rather than a licence negotiation. It is now a type error instead of a
> silent failure. See [Not supported](#not-supported).

## API reference

### `MediaSource`

```ts
{ uri: string; type?: 'file'|'hls'|'dash'|'progressive';
  headers?: Record<string,string>; cacheable?: boolean }
```

> **`'smooth'` was removed in 0.5.0. It was never implemented — both platforms fell
> back to progressive playback, which fails on real Smooth Streaming content.

### `Track`

```ts
{ id: string; source: MediaSource; title?, artist?, album?, artwork?, duration? }
```

### `PlaybackState`

```ts
{ status: 'idle'|'loading'|'ready'|'playing'|'paused'|'buffering'|'ended'|'error';
  position: number; duration: number; rate: number; muted: boolean;
  volume: number; buffered: number; inBackground: boolean; error?: string }
```

| Component | Props |
|---|---|

### Hooks

- `useVideoPlayer()` — returns `{ ref, controls, state, onState }` for `<Video>`. Pass `onState` to `<Video onStateChange={onState}>` or `state` stays at its initial value.
- `useAudioPlayer(initial?)` — `{ state, controls }` (`load/play/pause/stop/seek/setRate/setVolume/setMuted/setLoop/getState`).
- `useMusicPlayer(initialTracks?)` — `{ state, queue, controls }` (`setQueue/addTracks/removeTrack/skipTo/next/previous/play/pause/stop/seek/setRate/setVolume/setMuted/setRepeatMode/setShuffle/setRemoteControls/setBackgroundEnabled/getQueue/getState`).
- `usePlaybackState(state)` — derived `{ isPlaying, isPaused, isBuffering, isLoading, isEnded, hasError, progress }`.
- `useRemoteControls(cb)` — subscribes to lock-screen commands.

### Cache / downloads

- `DownloadManager.download(id, source)` / `removeDownload(id)` / `getDownloads()` / `clearCache()` / `getCacheSize()` — JS façade over `ObsidianCache` (TurboModule `NativeObsidianCache`, native `CacheNative`).
- `CacheNative` — direct TurboModule access (`ObsidianCache`) if you need raw promises.

### Web exports

- `Video` / `Audio` on web resolve to `src/components/Video.web.tsx` / `Audio.web.tsx` (HTML5). No native linking required.

### 0.5.0 - Web parity, iOS architecture, Android media session, and gates that were never there

> **This consolidates everything since `0.1.5`.** `0.3.0`, `0.3.1` and `0.4.0`
> were written during the work but never published, so they never existed for a
> consumer. They are folded into this single entry rather than shipped as a chain
> of versions nobody ever saw. Per-item status, including what is *not* verified,
> lives in [`progress.md`](./progress.md); the full plan with reasoning is in
> [`to-be-done.md`](./to-be-done.md).

**Breaking.**

| Change | Migration |
|---|---|
| iOS requires the New Architecture | `RCT_NEW_ARCH_ENABLED=1 pod install`. `pod install` now fails with these instructions rather than succeeding and failing at runtime. Android is unaffected. |
| `react-native >= 0.74.0` (was `>=0.73`) | The floor was never real: the package extends `BaseReactPackage`, which does not exist before 0.74. |
| `MediaSource.drmLicenseUri` removed | DRM is not implemented. Widevine needs a real session manager + licence server; FairPlay needs `AVContentKeySession`, a resource-loader delegate and the `fps` entitlement. |
| `MediaSourceType: 'smooth'` removed | Both platforms silently fell back to progressive, which fails on real `.ism` content. AVPlayer has no Smooth Streaming support at all. |
| `NativeObsidianVideo.onVideoReady` removed | Declared in the codegen spec, emitted by no platform. Read dimensions from `onStateChange` or `onLayout`. |
| `DownloadInfo.localExtension` replaced by `localUri` | An extension does not make a path and JS cannot know the cache directory. Nothing ever wrote the old field. |
| `MusicControls.setQueue` / `AudioControls.load` return `Promise<void>` | Both were already `async`; the declared type was the lie. `await` them. |

**Added**

- **`VideoHandle.flush(timeoutMs?)`** — resolves once the next native emission has
  been applied, giving the synchronous `getState()` a way to be awaited. Falls back
  to resolving after `timeoutMs` (default 1000) so it cannot hang on an idle or
  ended player. Available on web too.
- **`useVideoPlayer().onState`** — wire it to `<Video onStateChange={onState}>` and
  `state` becomes live. Identity is stable, so it never re-renders `<Video>` on its
  own account.
- **`DownloadManager.isSupported`** — a getter, not a constant, so it reflects the
  environment when read (`caches` is absent outside a secure context). Use it to
  hide a download UI rather than offer one that cannot work.
- **`CastProvider` + `CastManager.registerProvider()` + `isSupported`** — an honest
  casting seam. No SDK is bundled; that needs a Cast app ID and a device.
- **`RemoteCommand` gains `'stop'`** — the web media session emits it.
- **Six gates**, all runnable in CI, none of which existed before: `bundle:web`,
  `verify:ios`, `verify:android`, `verify:android:host`, `verify:ios:pod`,
  `verify:gates`.

**Removed (inert API, honest stubs instead)**

- DRM, Smooth Streaming — deleted rather than half-built.
- The Paper fallback claim for iOS video: it never worked. Interop is now correctly
  wired and documented; a real `RCTViewComponentView` is left as future work
  rather than shipped unverified.

#### Waves 3, 4 and 6 (formerly 0.4.0)

#### iOS New Architecture is now required, and it actually works (Wave 3)

**The iOS module could not compile.** Not "would misbehave" — the pod failed to
build. Four independent hard failures, none of which any existing check could
see, because nothing had ever compiled the Swift.

- **The TurboModule conformances named protocols that do not exist.** The Swift
  files declared `extension ObsidianAudio: ObsidianAudioSpec {}`. Codegen emits
  `@protocol NativeObsidianAudioSpec` — the name comes from the *spec file*, not
  from the string passed to `TurboModuleRegistry.getEnforcing`.
- **`#if RCT_NEW_ARCH_ENABLED` in Swift was a no-op.** It is a C preprocessor
  macro and Swift's `#if` tests compilation conditions, so the block was always
  compiled out. It read like a guard and provided none — which is why this
  survived being read carefully.
- **The bridging header imported the generated spec header**, which opens with
  `#ifndef __cplusplus / #error`. A bridging header is parsed as Objective-C.
- **The podspec declared `ReactCodegen`.** The pod is `React-Codegen`, so
  `pod install` failed outright.

What was *not* wrong is worth stating, because the obvious fix would have made
things worse: the three modules never needed `RCT_EXPORT_MODULE`.
`RCTTurboModuleManager` resolves them by class name, and `@objc(ObsidianAudio)`
already matches. Adding the usual `RCT_EXTERN_MODULE` shims would have been dead
code. Conformance does have to exist — but in Objective-C++, because
`RCTTurboModule` requires a C++ `getTurboModule:` that Swift cannot implement.
That lives in the new `ios/ObsidianMediaPlayerModules.mm`.

**`<ObsidianVideo>` was not on Fabric's component allowlist.** The video surface
is a Paper `RCTViewManager` rendered through Fabric's legacy interop layer, and
`RCTLegacyViewManagerInteropComponentView.isSupported:` checks a hardcoded list
that `ObsidianVideo` was not on — so it resolved to
`RCTUnimplementedViewComponentView` and rendered nothing, with no error. All
eight `VideoHandle` commands were also missing `RCT_EXPORT_METHOD`, which is how
the interop layer dispatches them, so they would have logged `No command found`
and done nothing. Both fixed. There is still no native Fabric component view:
interop is now correctly wired, and a real `RCTViewComponentView` is left as
future work rather than shipped unverified.

**Breaking:** iOS requires the New Architecture.

```bash
RCT_NEW_ARCH_ENABLED=1 pod install
```

`pod install` now fails immediately with these instructions if the variable is
unset, rather than succeeding and failing at runtime. Android is unaffected and
still works on both architectures. Previously the README claimed a Paper
fallback worked via RN's interop layer; it did not. See
[Not supported](#not-supported).

Also: `podspec` drops `RCT-Folly` and `React-RCTAppDelegate` (app-target pods a
library should not depend on) and adds `React-RCTFabric`; the
`SWIFT_OBJC_BRIDGING_HEADER` is now set explicitly rather than relying on a
filename convention; `ObsidianCache` no longer declares `addListener` /
`removeListeners` it can never use, so the spec and the class agree; and the
"native module is not linked" error now names `RCT_NEW_ARCH_ENABLED=1`, which is
the actual fix in almost every case.

**New gate: `npm run verify:ios`.** Runs RN codegen for real and cross-checks
the generated protocols against the Swift and Objective-C++ — protocol names,
spec-method coverage, the interop allowlist, the video command exports, the
podspec dependencies, the bridging header. Codegen is a pure Node function, so
this runs on any platform in about a second, and it goes red on all 12 of the
mutations above. It is a cross-check, not a build: it cannot prove the Swift
compiles, and `pod lib lint` remains unproven.

#### Android background playback is real now (Wave 4)

The foreground service owns the
shared `ExoPlayer` and the `MediaSession` (`MediaSessionService` +
`MusicPlaybackHolder`), so audio survives a JS reload / Fast Refresh, the
notification follows track changes, and lock-screen / headset / Wear OS / Auto
connect through the service binder. `setRemoteControls()` honours its argument
(play-pause / skip / seek gate both the notification actions and controller
commands), and every command reaches JS as `onRemoteCommand` in the
`{ command, payload }` shape iOS already sent — `useRemoteControls` works on
Android with no JS changes. The module also emits `onProgress` at 4 Hz (it
never did), sets `AudioAttributes` with focus handling, and `removeTrack` no
longer restarts the current song when an unplayed track is removed (same fix on
iOS; both mirror the web queue). `removeDownload` evicts per cache key and
`clearCache` no longer deletes files behind a live `SimpleCache`.

**Artwork/duration are rendered, not discarded (FG-6.4, Wave 6).** Android publishes
`MediaMetadata` (title / artist / album / artwork) on every `MediaItem` and
loads the notification large icon asynchronously; iOS sets
`MPMediaItemPropertyArtwork` (stale-fetch guarded) and prefers a declared
`Track.duration` until the item reports one.

**Casting stays a stub, but an honest one (FG-6.3, Wave 6).** `CastManager` gains a
`CastProvider` interface + `registerProvider()` and `isSupported`;
`connect()` without a provider rejects with an actionable error instead of
silently pretending. No SDK is bundled — that still needs a Cast app ID and a
device to develop against.

Behaviour changes: `CastManager.connect()` without a provider now rejects
(previously resolved and set local state); `removeDownload` / `clearCache`
resolve with `{ id, status, bytesFreed }` / `{ cleared, failures }` payloads
(previously `{}`-ish). Native changes need a real device to fully verify -
the Kotlin gate (`npm run verify:android`, RN 0.74 + 0.80) compiles all 9
`.kt` files; Swift, manifest merging and on-device behaviour still need CI /
a handset. Suite is 229 tests across 14 suites.

**Offline playback consults the cache (FG-5.1, Wave 5 - implementation landed,
device verification open).** `useMusicPlayer.setQueue` and `useAudioPlayer.load`
now resolve a downloaded track to a local copy before handing it to the player.
Three defects made the previous attempt a no-op:

- `setQueue` spread a new **top-level `uri`** onto each track. A `Track` has no
  such field - it has `source.uri` - so the cached path landed somewhere nothing
  reads and the source URL stayed in the field that *is* read.
- `useAudioPlayer.load` passed a media URI to `resolveUri(id)`, which matches
  against `DownloadInfo.id`. It could never match, so the audio path never
  consulted the cache at all.
- `resolveUri` tested `DownloadInfo.localExtension`, a field **nothing ever
  wrote**, and returned the source URL either way.

What that last one means on each platform, since it is not a stub:

| | Playback of a downloaded track |
|---|---|
| **iOS** | `localUri` - a real `file:` URL to the module's own copy, recorded in the index. |
| **Android** | The source URL. `SimpleCache` keys spans by URL and `CacheDataSource` serves them, so requesting the source URL *is* how a cached file is played. There is no per-download path to hand a player. |

`DownloadInfo.localExtension` is **replaced by `localUri`**: an extension does not
make a path, and JS cannot know the app's cache directory. Breaking for anyone
reading the old field, which was never populated.

Also fixed: an HLS download reported its **local** path as `uri`, so the source
URL was lost from the library entirely, and `getDownloads` stat'd a path derived
from the `.m3u8` manifest rather than the downloaded bundle - reporting 0 bytes
for completed downloads. Android eviction now uses the *normalised* cache key
rather than the raw URI string, so it stops silently removing nothing when
`Uri.parse` normalises differently. And `MediaSource.cacheable: false` - already
honoured by both native players - is now honoured by the JS lookup too.

There is deliberately **no** new `preferCache` flag: `cacheable` already means
this, and a second spelling would be one the platform ignores.

#### The web build, and the first real gates (formerly 0.3.1)

Two unrelated halves, both of them about the same thing: **things that were never
checked**. The Android module had never compiled, and the web build had never

**Fixed — the Android build could not configure.** An app consuming the package

**Added — a gate, because the two fixes above were both invisible to CI.**
`npm run verify:android` type-checks every `.kt` file against real `react-android`

**Web — importing the package no longer breaks web bundling**

`import { MusicPlayer } from 'obsidian-media-player'` took down every web target.
There were five separate causes, and only one of them was the one the original
audit named:

| | |
|---|---|
| `VideoNative.ts` | imported its codegen spec for real, so the bundle needed `react-native/Libraries/Utilities/codegenNativeComponent` — a path react-native-web does not have. A **bundler** error, unreachable from any runtime guard. |
| `MusicPlayerNative.ts`, `AudioNative.ts` | threw "native module is not linked" at **import** time, for apps that never touched audio. |
| `useMusicPlayer`, `useAudioPlayer`, `useRemoteControls` | imported `NativeEventEmitter`, which react-native-web does not implement. |
| `CacheNative.ts` | looked safe — it yields `undefined` on web and `DownloadManager` tolerates that — but its `require()` inside a never-executed New-Arch branch is a **static** edge, so the spec was still in the web graph. |

Because `index.ts` re-exports all of them unconditionally, every web app was
broken, not just the ones using media.

What shipped:

- **`<MusicPlayer>` and `useMusicPlayer` now work on web.** A real player over one
  `HTMLAudioElement`, reusing `core/PlaylistManager` for shuffle / repeat / cursor,
  so queue semantics match native by construction rather than by two
  implementations agreeing. `useAudioPlayer` too. See [Web](#web).
- **Importing the package is safe.** The native modules have `.web` stubs that are
  importable and throw only when you *call* them, with a message saying why. They
  never render, so a stray `<MusicPlayerNative />` is a no-op rather than a crash.
  `CacheNative.web.ts` exports `undefined` on purpose — a throwing stub would look
  "available" to `hasNativeCache()` and disable the browser's `CacheStorage`
  fallback.
- **`npm run bundle:web` + a CI job.** Bundles the whole public surface for the
  browser and fails if anything in the graph reaches for a native-only module. A
  bundle is the only thing that can catch this class of break; type checks and unit
  tests both pass on code that cannot be bundled. Run the full gate with
  `npm run verify`.
- `MusicControls`, `QueueSnapshot`, `AudioControls` and `MusicPlayerHandle` moved
  to `src/types.ts`, shared by both platforms — otherwise the web build would need
  its own copy of each, which is how `Video.web.tsx` came to miss `flush`.

Three ordering bugs in the new web queue were found by the tests that pin them and
fixed: `skipTo` treated a track index as a cursor (wrong track under shuffle),
`addTracks` never added to the play order (new tracks permanently unreachable), and
`removeTrack` left the play order holding pre-deletion indices (harmless with
shuffle off, corrupting under shuffle).

**Not verified:** no browser has run any of this. The 38 web-player tests and the
21 resolver tests drive a fake `HTMLAudioElement`, a stubbed `fetch` and a
counting `URL.createObjectURL` double, which proves the logic and the object-URL

**Web — `MediaSource.headers` now works for progressive sources**

HTML media elements have no header API, so a source authenticated by a bearer token
simply could not be expressed as `src` on web. The web build now fetches such a
source itself and hands the element an object URL:

```ts
// Works on iOS, Android and web.
<Video source={{ uri: 'https://cdn.test/clip.mp4', headers: { Authorization: `Bearer ${t}` } }} />
```

| | |
|---|---|
| `progressive` / `file` / untyped | Fetched with the headers, buffered, played. |
| `hls` / `dash` + headers | **Refused with an error.** A manifest is not the media, so there is no single blob to hand over — buffering it truncates the stream. Use a signed query string or a same-origin proxy. |
| No headers | Unchanged: a plain `src` assignment. No fetch, no buffering, no extra CORS requirement. |
| Object URLs | Revoked when the source changes and on unmount. A 50-track header-auth queue holds one blob, not fifty. |

Two costs worth knowing before you use it: the file is **fully buffered** before
playback starts (a 200 MB video is a 200 MB allocation), and `fetch` is subject to
the same-origin policy, so the origin has to send `Access-Control-Allow-Origin`.
Neither is fixable from the client.

**Web — `<Audio>` reported no playback state at all**

Found while implementing the above. `Audio.web.tsx` created its element and
attached **no media event listeners**, so on web `state.status` stayed `idle` for
the life of the component, `position` / `duration` never moved, the declared
`onEvent` prop was never called, and changing the `source` prop did nothing (the
element was built once, on mount). All nine media events are now wired, and the
source re-resolves when it changes.

**Web — `navigator.mediaSession` now works**

`useRemoteControls` was a documented no-op on web. It now bridges the browser's OS
media session, so hardware media keys, a lock screen and car stereo drive the web
queue. The web player also publishes the now-playing track, which made
`Track.artwork` do real work for the first time — native followed in 0.5.0
(iOS `MPMediaItemPropertyArtwork`, Android notification large icon +
`MediaItem` metadata).

| MediaSession | `RemoteCommand` |
|---|---|
| `play` / `pause` | `play` / `pause` |
| `nexttrack` / `previoustrack` | `next` / `previous` |
| `seekbackward` / `seekforward` / `seekto` | `seek` with `{ position }` |
| `stop` | `stop` (new in the union) |

The three seek actions send a *delta*; native sends an absolute position, so the
hook resolves them against `getState`. All eight actions are registered, each
individually feature-detected, so one action a browser does not implement costs
neither the other seven nor an exception. Nothing is touched when `navigator` is
absent, so SSR is safe.

`navigator.mediaSession` is a document singleton, so all of it lives in one module
(`utils/webSession.ts`) — otherwise the hook and the player would overwrite each
other's handlers with no error.

**Web — offline downloads actually work now**

`DownloadManager` on web was three stubs: `download` called `cache.add(uri)` inside
an empty `catch {}`, `removeDownload` did nothing (the comment admitted it), and
`getDownloads` returned `[]`. A user could click download, see no error, and have
nothing saved.

The root problem was that **CacheStorage has no notion of an id** — `cache.add()`
keys by media URL, so there was nothing for `removeDownload(id)` to match.
Entries are now stored under a synthetic key derived from the id
(`https://obsidian-media-player.invalid/download/<id>` — `.invalid` is reserved by
RFC 2606, so the key can never resolve or collide), which makes lookup, deletion
and enumeration work from the id alone, across reloads. The fetch is done by hand
rather than by `cache.add()`, which is also what lets it send `MediaSource.headers`
and attach a content type and byte count to the entry.

| | Before | Now |
|---|---|---|
| Failure | `catch {}` — silent | Rejects, naming CORS / 401 / 403 / 404 |
| `getDownloads()` | `[]` | Enumerates the cache |
| `removeDownload(id)` | no-op | Deletes by id |
| `getCacheSize()` | `0` | Sum of stored bytes |
| `hls` / `dash` | "succeeded", unplayable | Refused |
| Capability | assumed | `DownloadManager.isSupported` getter |
| Return value | `void` | `DownloadInfo` |

**Also fixed**

- A superseded header-auth load that *failed* used to surface a playback error for
  a track the user had already skipped past. Loading is asynchronous now, so a
  slow fetch can land after a `next()`; those resolutions are discarded instead.

functions at the start of the audit.

| Bug | Symptom |

**Added**

- **`VideoHandle.flush(timeoutMs?)`** — resolves with the state once the next
  native emission has been applied, giving the synchronous `getState()` a way to
  be awaited. Falls back to resolving after `timeoutMs` (default 1000) so it
  cannot hang on an idle or ended player. Available on web too.
- **`useVideoPlayer().onState`** — wire it to `<Video onStateChange={onState}>`
  and `state` becomes live. Identity is stable, so it never re-renders `<Video>`
  on its own account.
- `useMedia().controls` is now a stable delegating facade, safe to capture in a
  callback or dependency array.
- `<Audio>` and `<MusicPlayer>` handles are identity-stable like `<Video>`, and
  their `onEvent` now fires on every native emission rather than only on status

**Native**

- **`onBuffering` now fires on Android and iOS.** It was declared in the codegen
  spec and registered in `getExportedCustomDirectEventTypeConstants`, but no

### 0.2.0 — Android native build fix (`prefab` opt-in)

Fixes the fatal app build failure on New Architecture:

```
> Task :obsidian-media-player:configureCMakeRelWithDebInfo[arm64-v8a] FAILED
CMake Error at CMakeLists.txt:28 (find_package):
  Could not find a package configuration file provided by "ReactAndroid" with
  any of the following names:
    ReactAndroidConfig.cmake
    reactandroid-config.cmake
```

- **`android/build.gradle` — `buildFeatures { prefab = true }`** is the actual fix. `find_package(ReactAndroid CONFIG)` in a `com.android.library` module is resolved through AGP's prefab mechanism, and prefab is opt-in per module. `react-native-gradle-plugin` only injects `-DREACT_ANDROID_DIR` and flips `prefab` on for `com.android.application` (`NdkConfiguratorUtils.kt`, gated on `withPlugin("com.android.application")`), so a library gets nothing. ReactAndroid publishes the prefab packages itself (`ReactAndroid/build.gradle` → `buildFeatures { prefab true }`); without the consumer opting in, AGP emits no `ReactAndroidConfig.cmake` and passes no `CMAKE_FIND_ROOT_PATH` to CMake — exactly what the failing invocation showed.
- **Removed the library's own `buildscript { }` block.** It pinned `com.android.tools.build:gradle:8.1.1`, dragging a second, much older AGP into a Gradle 9 / AGP 8.12+ build. The `apply plugin:` calls now resolve from the host's buildscript classpath, which is the supported pattern for RN libraries.
- **SDK / NDK now mirror the host** instead of hardcoding `compileSdk/targetSdk 34` + `minSdk 21`. `minSdk 21` would have failed the manifest merger next (`uses-sdk:minSdkVersion 21 cannot be smaller than version 24 declared in library`) against `react-android`. Values are read from the app's root `ext` (`compileSdkVersion`/`minSdkVersion`/`targetSdkVersion`/`ndkVersion`), overridable via `ObsidianMediaPlayer_<name>` in `android/gradle.properties`, falling back to 36/24/36.
- **Pins the host's `ndkVersion`.** Previously this module silently fell back to AGP's *default* NDK and downloaded a second one (`27.0.12077973`) while the app built with `27.1.12297006` — two different `libc++_shared.so` in one APK.
- **`api("com.facebook.react:react-android")`** replaces `implementation("com.facebook.react:react-native:+")`. `ObsidianVideoManager : SimpleViewManager<...>` and `ObsidianAudioModule : ReactContextBaseJavaModule` are public and expose RN types, so `implementation` left `react-android` off the consumer's compile classpath. `react-android` is also the prefab-publishing artifact; the `react-native` coordinate only resolves because the RN plugin substitutes it.
- **`abiFilters` follow the host's `reactNativeArchitectures`** instead of always forcing four ABIs.
- `android/CMakeLists.txt` — quoted `${CODEGEN_JNI_DIR}` (Windows checkouts with spaces), de-duplicated the warning flags, and made `-Werror` opt-in via `-DOMP_ENABLE_WERROR=ON`.
- `.npmignore` — added `android/.cxx/`; AGP's CMake scratch dir was shipping into consumers' `node_modules` with absolute NDK paths baked in.

After upgrading, wipe the app's native state and rebuild (`expo prebuild --clean` → `expo run:android`). Your CMake configure line should now contain a `-DCMAKE_FIND_ROOT_PATH=` prefab argument and only one NDK should be installed.

> **Note on `bob build` output.** `bob build` prints *"The esm option is disabled, but the `exports['.'].import` field is set in `package.json`. This is likely a mistake."* **This warning is a false positive here — do not "fix" it by setting `esm: true`.** With `esm: false`, bob writes a `{"type":"module"}` marker into `lib/module/` and `{"type":"commonjs"}` into `lib/commonjs/`, which is precisely what makes the `import` / `require` conditions resolve to genuine ESM and CJS. Setting `esm: true` *skips* those markers, and since the root `package.json` has no `"type"`, Node would then parse ESM-syntax `.js` as CJS and throw.

### 0.1.3 — Android New Architecture / Codegen fix

Fixes the fatal app build failure (`add_subdirectory ... android/build/generated/source/codegen/jni/ which is not an existing directory` → `react_codegen_ObsidianMediaPlayerSpec which is not built by this project` → `:app:configureCMakeRelWithDebInfo` fails):

- `codegenConfig.type`: `"components"` → `"all"` (`package.json`) — `src/specs/` holds 3 TurboModules + 1 Fabric component; the old value silently dropped the TurboModule specs.
- `android/build.gradle` now applies `com.facebook.react` with `react { libraryName = "ObsidianMediaPlayerSpec"; codegenJavaPackageName = "com.obsidianmediaplayer" }` — this is what makes the app build generate the missing `codegen/jni/` + `codegen/java/` output. Added `externalNativeBuild/cmake` wiring.
- Added `android/CMakeLists.txt` + `android/src/main/jni/OnLoad.cpp` — builds `libObsidianMediaPlayerSpec.so` and links `react_codegen_ObsidianMediaPlayerSpec`. Both are guarded (`if(EXISTS ...)`, `__has_include`) so Old Architecture / Paper builds without Codegen output still compile.
- `ObsidianMediaPlayerPackage.kt` now extends `BaseReactPackage` (was legacy `ReactPackage`) with `getReactModuleInfoProvider()` so Audio / Music / Cache resolve as TurboModules; `<ObsidianVideo>` stays on the Paper `ViewManager` with automatic Fabric interop.
- Fixed Kotlin `optString(..., null)` type-mismatch warnings (`ObsidianVideoView`, `ObsidianAudioModule`, `ObsidianMusicPlayerModule`, `ObsidianCacheModule`).

After upgrading, clean the app's native state and rebuild (`expo prebuild --clean` → `expo run:android`). Do not hand-create `android/build/generated/...` — an empty directory does not define the `react_codegen_*` target.

## Not supported

Stated plainly so you do not build on it. These were removed rather than left as
non-functional API surface — see `to-be-done.md` for the reasoning.

| Feature | Status | Notes |
|---|---|---|
| **DRM (Widevine / FairPlay)** | **Not supported** | `MediaSource.drmLicenseUri` was removed in 0.5.0. It was accepted, threaded through every native load path, and then discarded — so protected content failed as a bare network error instead of a licence failure. Widevine needs a real `DefaultDrmSessionManager` + licence server; FairPlay needs `AVContentKeySession`, an `AVAssetResourceLoaderDelegate` and the `com.apple.developer.fps` entitlement. **Neither is implementable without infrastructure to develop against.** |
| **Smooth Streaming** | **Not supported** | `type: 'smooth'` was removed in 0.5.0. Both platforms silently fell back to progressive playback, which fails on real `.ism` content. AVPlayer has no Smooth Streaming support at all, so this could never have been a cross-platform feature. |
| **Casting (Chromecast / AirPlay picker)** | **Stub** | `CastManager` has a provider interface (`registerProvider`, `isSupported`) but no SDK behind it: `discover()` returns `[]` and `connect()` rejects until one is registered. Note *system* AirPlay already works on iOS — `AVAudioSession` opts in via `.allowAirPlay` — so you can hand off to an AirPlay receiver; you just cannot drive discovery/pick from the app. |
| **Android lock-screen controls** | **Supported since 0.5.0** | `MediaSessionService` with a `MediaStyle` notification (prev / play-pause / next, honouring `setRemoteControls`), controller commands gated by the same options, and `onRemoteCommand` in the `{ command, payload }` shape iOS sends — `useRemoteControls` works on Android with no JS changes. |
| **Android background playback** | **Supported since 0.5.0** | The service owns the shared `ExoPlayer` + `MediaSession`, so audio survives a JS reload and the notification follows track changes (title / artist / artwork). Process death still loses the queue — the queue lives in the JS-side module — and recovery is a relaunch, not a restore. See `to-be-done.md` FG-4.0. |
| **Audio focus / interruptions** | **Partial** | Android requests audio focus (`AudioAttributes`, duck/pause on loss) and pauses on headset disconnect. iOS still only configures the session category — no interruption / route-change handling on either platform beyond that. |
| **DSP (EQ, ReplayGain, effects, analysis)** | **Not implemented** | No EQ, gain normalisation, effects, crossfade, gapless, pitch control, waveform or FFT exists in any form. This is a decision (`to-be-done.md` D5), not a gap — on iOS it is constrained by `AVPlayer` having no insertable processing graph. |
| **Android offline playback** | **Not wired** | Downloads populate the disk cache, but nothing resolves a cached URI at playback time — the player always fetches the original URL. |
| **Web offline downloads** | **Progressive only** | Since 0.5.0, backed by `CacheStorage` and keyed by download id, so `getDownloads` / `removeDownload` / `getCacheSize` work as they do natively. `hls` / `dash` are refused — a segmented stream cannot be one cache entry. `MediaSource.headers` is honoured. Still subject to CORS (the origin must send `Access-Control-Allow-Origin`) and to the browser's storage quota, and unavailable outside a secure context — check `DownloadManager.isSupported`. |
| **Web `MediaSource.headers`** | **Progressive only** | Since 0.5.0, a `headers` source is fetched by the web build (`fetch` → blob → object URL), so `Authorization` works for `progressive` / `file` / untyped sources. It still does **not** work for `hls` / `dash`: a segmented stream cannot be buffered into one object URL, and those sources are refused with an error rather than silently truncated. A header-auth source also needs the origin to send `Access-Control-Allow-Origin` — `fetch` is subject to the same-origin policy, so no client-side code can work around it. Whole-file buffering is the cost: a 200 MB video is a 200 MB allocation before playback starts. |
| **Web background audio / `setBackgroundEnabled`** | **No-op** | A browser has no audio session. Playback continues while the tab lives, but there is no equivalent of an iOS audio session or an Android foreground service, and nothing survives the page being closed. The prop is accepted and ignored so cross-platform code needs no branch. |
| **iOS Old Architecture (Paper)** | **Removed** | 0.5.0. iOS requires `RCT_NEW_ARCH_ENABLED=1`; `pod install` fails without it. Android still supports both. The video surface is a Paper `RCTViewManager` mounted through Fabric's legacy-view-manager interop layer, so there is no `RCTViewComponentView` subclass — functional, with the interop layer's prop-diffing overhead, but it emits a deprecation warning and is a candidate for a native Fabric view later. See `to-be-done.md` Wave 3. |
| **Picture-in-picture** | **Not modelled** | No spec field, no native handling. |
| **Subtitles / captions** | **Not modelled** | No `MediaSource` field, no native handling. |

**iOS requires the New Architecture.** Set `RCT_NEW_ARCH_ENABLED=1` in the
environment that runs `pod install`:

```bash
RCT_NEW_ARCH_ENABLED=1 pod install
```

Without it `pod install` fails immediately with these instructions, rather than
succeeding and then failing at runtime. This is a change from earlier versions,
which claimed a Paper fallback worked via RN's interop layer. It did not: the
TurboModule specs in `src/specs` are only registered under Fabric, the Swift
`extension ...: Spec {}` conformances named protocols codegen never emits, and
`<ObsidianVideo>` was never on the interop layer's component allowlist. See
`to-be-done.md` Wave 3 and decision D1.

Android is unaffected — it works on both architectures (`BaseReactPackage`
resolves on each). `lib/` is generated by `react-native-builder-bob`
(`commonjs`/`module`/`typescript`).

## Scripts

```bash
npm run typecheck   # tsc --noEmit
npm run lint        # eslint src --max-warnings=0
npm run prepare     # bob build  (also prepack)
npm test            # jest - 229 tests / 14 suites
npm run codegen     # react-native codegen - regenerates ObsidianMediaPlayerSpec
npm run bundle:web  # esbuild web bundle of the full public surface - the web gate
npm run verify      # typecheck + lint + test + bundle:web + verify:ios

npm run verify:android      # Kotlin type-check of android/src - no NDK, no Gradle, no device
npm run verify:android:host # Gradle assembleRelease in a scaffolded RN host app
npm run verify:ios          # runs RN codegen, cross-checks it against ios/ - runs anywhere
npm run verify:ios:pod      # pod lib lint (macOS only)
npm run verify:gates        # prove every gate goes red on a known-bad input
```

> `npm run verify:ios` is the iOS counterpart to `verify:android`, and it exists
> for the same reason. Nothing compiled the Swift, so four hard build failures
> shipped: the conformances named protocols codegen never emits
> (`ObsidianAudioSpec` vs `NativeObsidianAudioSpec`), the podspec declared a pod
> called `ReactCodegen` that does not exist, all eight video commands were
> missing `RCT_EXPORT_METHOD`, and the bridging header imported an
> Objective-C++-only header. Codegen is a pure Node function, so this gate runs
> anywhere — it does not need a Mac. It is **not** a substitute for a build: it
> cross-checks the generated contracts against the native sources and cannot
> prove the Swift compiles.

> `npm run verify:android` compiles the Android module's Kotlin against real
> `react-android` and `androidx.media3` artifacts, across a **version matrix**
> (RN 0.74 and 0.80). It exists because the Gradle build aborts at
> `configureCMakeRelWithDebInfo` before Kotlin is ever compiled, so Kotlin errors
> are invisible while the native build is broken — which is how two hard compile
> errors and a false `react-native` floor reached published versions. It covers
> no manifest merging, no CMake/NDK and no runtime, so it does not replace a
> Gradle CI job. See `to-be-done.md` FG-0.6.

`bundle:web` is the one people skip and shouldn't. It resolves `react-native` to
`react-native-web` and prefers `.web.*` files exactly as Metro does, so it fails if
any module reachable from `index.ts` still pulls in a native-only import. That
check is the reason the web build works at all, and it cannot be replaced by
anything in the list above.

### CI — three gates

`npm run verify` is JS and web only: it cannot see a single line of the ~1,100
lines of Kotlin and ~1,100 of Swift in this module. `.github/workflows/ci.yml`
therefore runs three jobs.

| Job | Command | What it catches |
|---|---|---|
| `js` | `npm run verify` | type errors, lint, regressions, a web-only import creeping back in |
| `android` | `verify:android` then `verify:android:host` | unresolved Kotlin references, and then everything the local gate cannot see: manifest merging (including the `FOREGROUND_SERVICE_MEDIA_PLAYBACK` fix), resource linking, the CMake/NDK compile of `OnLoad.cpp` |
| `ios` | `npm run verify:ios` | a malformed podspec, a glob that stops matching, Swift that does not compile |

`verify:android:host` scaffolds a throwaway RN host app with the community CLI
and builds the module inside it, because the module resolves `ndkVersion`,
`compileSdkVersion` and the ABI list from the app's `rootProject.ext` and cannot
be built standalone. It requires an AAR on disk, not just exit 0.

`verify:gates` is the interesting one: it injects a known-bad change into each
gate, asserts the gate goes red *and* that the output contains the expected
error, then restores the file. A gate that has never failed is not a gate, and a
gate that is red because its own environment is broken has proven nothing about
the code. CI runs the fast subset; `--full` adds the Gradle and pod probes.
